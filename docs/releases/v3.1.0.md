# v3.1.0 — 2026-11-15

Главное: **серверы в конфиг отбираются SQL-запросами**, теги переехали в
отдельную таблицу, появился чекер, который определяет провайдера и признак
датацентра. Деплой больше не останавливает проверку.

## Что нового

### SQL вместо фильтров

В шаблоне конфига вместо списка серверов теперь стоит запрос:

```json
"outbounds": [
  { "sql": "SELECT s.line FROM servers s JOIN server_tags t ON t.key = s.key
            WHERE t.tag = 'alldeploy' AND t.kind = 'service' AND t.passed = 1
              AND s.available = 1 AND s.excluded = 0
            ORDER BY t.ping_ms IS NULL, t.ping_ms LIMIT 5" },
  "alldeploy-reserved"
]
```

Строки, которые вернула база, становятся узлами конфига. Запрос выполняется
только на чтение (`mode=ro` + `PRAGMA query_only`).

Готовые рецепты — в [docs/database.md](../database.md#sql-рецепты-для-фильтров).

### Теги в отдельной таблице

`server_tags` заменила строковые колонки `capabilities` и
`service_pings`. Одна строка на пару (тег, сервер) с задержкой до цели.
Поиск по тегу идёт по индексу, а не сканированием всей таблицы.

```sql
SELECT tag, kind, COUNT(*) FROM server_tags WHERE passed = 1 GROUP BY tag, kind;
```

### Чекер `ip_info`: провайдер и признак датацентра

Google и Claude не любят подключения с серверных хостингов. Новый чекер
определяет ISP, город, регион и номер AS, и ставит теги:

```
isp-megafon  city-novosibirsk  as-56630  dc  res  mobile
```

Справочник провайдеров (`asn_info`) **расширяется сам**: наблюдения
копятся по номеру AS, и после нескольких проверок провайдер получает
устойчивый вердикт — дальше все его серверы классифицируются без запросов.

### Деплой — список независимых блоков

```yaml
deploy:
  - type: github
    name: main
    repo: owner/repo
    token: env:GH_DEPLOY_TOKEN
    templates: sbc-1.14.json
  - type: local
    name: local
    path: output
  - type: whitelist
    name: whitelist
    path: output/whitelist.txt
```

Нет блока — нет деплоя. Появился тип `whitelist` — выгрузка живых серверов
из базы построчно.

### Деплой не останавливает проверку

Раньше `Pipeline.run()` ждал опустошения очереди с лимитом в час, по
истечении глушил проверку и только потом публиковал: на очереди в 200 тысяч
серверов конфиг уезжал с тем, что успели проверить. Теперь публикация идёт
отдельной задачей по таймеру и берёт снимок базы, а проверка продолжается.

## Ломающие изменения

- **`deploy` стал списком.** Старая форма с `deploy.enabled`, `local`,
  `repo`, `template` больше не читается. Поля `source`, `create_repo`,
  `private` убраны.
- **`core.best_top` и `core.best_reserve` удалены.** Тегов `-best` и
  `-reserve` больше нет: уровень сервера задаётся сортировкой по задержке
  до цели (`LIMIT 5` — лучшие, `LIMIT 21 OFFSET 5` — резерв).
- **Ключ `filter` в шаблоне заменён на `sql`.** Старый `filter` по
  ключевым словам больше не применяется при сборке из SQL-выборки.
- **Имена узлов изменились** на `<флаг> <протокол> <10 hex от ключа>`,
  например `🇩🇪 vless dcff8b1b96`. Прежние имена из подписок больше не
  используются: они совпадали у разных серверов и ломали sing-box.

## Обновление

1. Подтянуть код.
2. Перенести `deploy` в новую форму (список блоков) — см.
   [docs/config.md](../config.md#деплой).
3. Удалить из `config.yaml` `best_top` и `best_reserve` — они больше не
   читаются.
4. Запустить любой прогон: таблицы `server_tags` и `asn_info` создаются
   сами, старые `capabilities`/`service_pings` переносятся автоматически.

База `source/servers.db` совместима: миграция добавляет колонку `kind` и
заполняет теги из существующих колонок при первом запуске.

## Проверено

- Сборка конфига на живой базе: 52 ссылки → 29 узлов, группы без пустых.
- Все блоки деплоя (`github`, `local`, `whitelist`) выполняются.
- `ip_info` на реальных серверах: `isp-melbikomas-uab / city-palermo /
  as-56630 / dc`, `isp-the-constant-company / city-osaka / as-20473 / dc`.
- Экспорт whitelist: 52 строки, метки сервисов на месте, гео-теги в имена не
  попадают.
