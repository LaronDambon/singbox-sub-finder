# Логи

- Логи записываются в папку `logs/`.
- Логирование настроено с ротацией и разделением по уровням: `app.log`,
  `info.log`, `warning.log`, `error.log`.

## Архив аномальных батчей: logs/singbox/

Обычный прогон следов не оставляет. Собранный конфиг батча удаляется сразу
после проверки, а вывод процесса sing-box живёт только в оперативной памяти и
исчезает вместе с ним. Пока всё идёт хорошо, это правильно: батчей за цикл
сотни, и писать каждый на диск значило бы убивать SSD перезаписью.

Но когда батч кончается ничем, разбираться не по чему. Так выглядит сбой, при
котором непонятно ни что было в конфиге, ни что сказал sing-box:

```
WARNING батч 42 (50 серв.): ответили 0/50 (живых 0, мёртвых 0),
        не отозвались 50, no_results, 0.1s
WARNING Батч 42: sing-box не вернул ни одного результата
```

Поэтому подозрительные батчи сохраняются целиком:

```
logs/singbox/b0042-20261108T124750/
    batch.json     собранный конфиг батча — что именно читал sing-box
    singbox.log    stdout+stderr процесса целиком, как есть
    meta.json      исход, код возврата, время, размер, версия
```

Идентификатор печатается в общем логе рядом с предупреждением, поэтому связь
двусторонняя:

```
WARNING Батч 42: сохранён в logs/singbox/b0042-20261108T124750
```

По этому идентификатору из `warning.log` всегда можно найти детали, а из
`meta.json` — понять, откуда пришла запись.

## Что именно сохраняется

Порог задаётся настройкой `singbox.keep_failed_batches`:

| Значение | Что попадает в архив |
|---|---|
| `off` | ничего |
| `error` | только сбои: `no_results`, `config_error`, `spawn_error` |
| `warning` | сбои плюс подозрительные `partial` (молчит четверть батча и больше) |
| `info` | вообще все батчи, включая штатные |

Значение по умолчанию — `error`: штатный прогон не пишет ничего.

Сколько записей хранить, задаёт `singbox.keep_failed_batches_limit`
(по умолчанию 200). Старые удаляются автоматически. Значение `0` выключает
архивацию целиком — вместе с накоплением вывода в памяти.

```yaml
singbox:
  keep_failed_batches: error
  keep_failed_batches_limit: 200
```

## Почему вывод копится в оперативной памяти

Вывод процесса складывается в память и уходит на диск **только** при
аномалии. Писать каждый батч в файл и удалять его при успехе значило бы
перезаписывать SSD на каждом прогоне.

На батч отводится 4 МБ; при превышении хвост отбрасывается, и в
`singbox.log` появляется строка об обрезке. Ограничение нужно на случай
патологического вывода: без него один зацикленный батч съел бы память всего
процесса.

## Что смотреть при разборе

`meta.json` в первую очередь:

- `returncode` — код возврата процесса. `None` означает, что процесс вообще
  не запустился; `127` — не нашлись библиотеки; `1` — sing-box упал сам;
- `outcome` — как классифицирован исход;
- `elapsed` — время жизни батча. Доли секунды означают смерть на старте, а не
  «серверы не отвечают»;
- `fatal_lines` — строки, которые коллектор счёл фатальными;
- `silent` — сколько серверов не отозвалось.

Дальше `singbox.log` — там полный вывод, включая то, что коллектор не
распознал. Именно в нераспознанных строках чаще всего и лежит причина.
