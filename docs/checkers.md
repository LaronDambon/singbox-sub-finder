# Проверка серверов и стран

Реализация по мотивам [Throne](https://github.com/throneproj/Throne) (core/server/test_utils/speedtest_utils.go):
- **один** процесс sing-box на батч прокси: каждому прокси — свой mixed-inbound на 127.0.0.1 и правило маршрутизации inbound → outbound, т.е. локальный порт жёстко привязан к своему конфигу (у Throne то же самое через outbound.DialContext в одном запущенном ядре);
- потоки Python параллельно стучатся в свои порты (COUNTRY_CHECK_CONCURRENCY, по умолчанию 8; в Throne — countryConcurrency=5);
- страна определяется одним лёгким запросом через цепочку: Cloudflare cdn-cgi/trace → api.ip.sb/geoip → ipinfo.io/json (вместо списка серверов speedtest.net, который блокирует датацентровые IP и давал ~40% отказов);
- ISO-код сразу превращается в эмодзи флага и пишется в базу (колонка country), поэтому повторных проверок для известных стран нет.

Если страна уже известна (эмодзи в имени или запись в базе) — сервер вообще не отправляется на проверку.

# Глубокие данные об IP: чекер `ip_info`

Одной страны для отбора мало: Google и Claude не любят подключения с
серверных хостингов, и нужен провайдер плюс понимание, домашний это IP или
датацентр.

Чекер-дополнение (`decides_availability = False`): он не решает, жив ли
сервер, а вешает на него теги, которые потом работают как фильтр.

## Откуда данные

Один процесс sing-box на батч, по mixed-inbound на каждый прокси — та же
схема, что у `country`. Потоки Python стучатся каждый в свой порт.

Цепочка источников, первый ответивший побеждает:

| Источник | Что даёт |
|---|---|
| `ip-api.com` | ISP, org, AS, город, регион, `hosting`/`proxy`/`mobile` |
| `ipinfo.io` | org (AS + провайдер), город, регион |
| `api.ip.sb` | isp, organization, город, регион |

`2ip.io` не годится: страница рендерится JavaScript'ом, по обычному HTTP
приходит пустая оболочка (503 + loader).

## Теги

| Тег | Значит |
|---|---|
| `isp-megafon` | провайдер |
| `city-novosibirsk` | город |
| `region-sicily` | регион, если отличается от города |
| `as-56630` | номер автономной системы |
| `dc` | датацентр |
| `res` | не датацентр |
| `mobile` | мобильный оператор |

Пишутся в `server_tags` с `kind = 'geo'` — они не участвуют в отборе
сервисов (там `kind = 'service'`), но по ним можно фильтровать.

## Как решается `dc` / `res` / `mobile`

Готового бесплатного справочника с таким признаком нет: `ipapi.is` отдаёт
`is_datacenter` только в платном тарифе, у `ipinfo.io` `company.type`
тоже платный, а `PeeringDB` классифицирует по роли в пиринге — у MegaFon
(домашний ISP) и у Vultr (хостинг) там одинаковый `NSP`.

Поэтому работает накопление наблюдений:

1. `hosting`/`proxy` от ip-api.com — их классификация конкретного IP;
2. устойчивый `kind` ASN из таблицы `asn_info` (выученный или встроенный);
3. номер AS во встроенном списке хостинговых (OVH, Hetzner, Vultr,
   DigitalOcean и ещё ~40);
4. `PeeringDB` `info_type: Cable/DSL/ISP` → `res`;
5. если источник умеет отвечать про hosting и сказал «нет» → `res`;
6. иначе тега нет — честное «неизвестно», а не выдуманное `res`.

### Авторасширение справочника

Каждая проверка приносит флаги `hosting`/`mobile`. Они копятся в
`asn_info` голосами по номеру AS. Набралось `learn_min_votes` (3)
наблюдений и совпало `learn_ratio` (0.8) — провайдер получает `kind`, и
дальше все его серверы классифицируются без запросов.

Новый хостинг появляется в подписках → три его сервера проверяются → ASN
получает `dc` → дальше отсекается фильтром без правки кода.

## Настройки

```yaml
ip_info:
  enabled: true
  concurrency: 8
  timeout: 10.0
  extra_hosting_asns: ""   # свои номера AS через запятую
  learn_min_votes: 3
  learn_ratio: 0.8
  peeringdb: true
```

Повторно сервер не проверяется, если у него уже есть гео-теги: провайдер
меняется редко, а зонд стоит один запрос через прокси.
