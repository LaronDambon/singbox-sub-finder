# Конфигурация

Настройки разделены на две части: **обычные** — в `config.yaml`, **секреты** — в
`.env`. Это не стилистическое деление: `config.yaml` коммитится и читается
человеком, `.env` лежит под `.gitignore` и содержит только то, что нельзя
показывать.

## config.yaml

Лежит в корне репозитория. Настройки сгруппированы по инструментам, у каждой
есть описание, единица измерения и значение по умолчанию:

```yaml
singbox:
  checkers:
    reachability:          # до каких целевых сайтов дозванивается прокси
      urls_file: config/reachability_targets.json
      concurrency: 8       # сколько прокси обрабатывать параллельно
      max_ping_ms: 500     # максимальный TTFB, мс
      timeout: 6.0         # таймаут одного целевого запроса, сек
```

Группа — это инструмент: настройки одного чекера лежат в
`singbox.checkers.<имя>`, общее ядро — в `singbox`. Значения по умолчанию уже
рабочие, поэтому файл нужен только чтобы переопределить нужное.

Управление файлом:

```bash
python -m pipeline config init     # создать config.yaml с комментариями
python -m pipeline config show     # что действует сейчас и откуда взято
python -m pipeline config export   # напечатать шаблон в stdout
```

`show` печатает источник каждого значения и маскирует секреты — им можно
проверять, почему настройка не применилась.

Схема настроек — [config/config.py](../singbox-subscribe/config/config.py):
единственное место, где настройка определена (тип, умолчание, описание,
секретность). Точка сборки — [settings.py](../singbox-subscribe/config/settings.py).

## .env

Только секреты. Четыре переменные, и ни одна не обязательна сама по себе:

| Переменная | Для чего | Нужна, если |
|---|---|---|
| `GH_DEPLOY_TOKEN` | публикация конфига в GitHub (Contents: read+write) | включён GitHub-деплой |
| `GH_READ_TOKEN` | чтение приватного репозитория с подпиской | подписка приватная |
| `GEMINI_API_KEY` | проверка доступа к Gemini через API | включён чекер `api_service` |
| `OPENROUTER_API_KEY` | проверка доступа к OpenRouter через API | включён чекер `api_service` |

`.env.example` в корне — шаблон ровно с этими именами.

В `config.yaml` секретов нет. Если ключ всё же вписать туда, значение не
применится, а в лог уйдёт предупреждение.

## Приоритет слоёв

От сильного к слабому:

1. аргументы CLI,
2. системное окружение,
3. `config.yaml`,
4. значения по умолчанию из схемы.

`.env` в этом списке **отсутствует**: это не слой настроек, а хранилище
секретов. Обычная настройка читается только из `config.yaml`, и переменная
окружения с прежним именем (скажем, `singbox.enabled_checkers` или `log.level`) её не
перебьёт. Если такие строки остались в вашем `.env` от старой установки — их
можно удалить, они молча ничего не делают.

## Раскладка: код отдельно, файлы отдельно

Внутри пакета — только исполняемый код. Всё, что пользователь правит или
накапливает, лежит в **каталоге данных**, отдельно от программы:

```
<каталог данных>/                     Windows: %LOCALAPPDATA%\singbox-subs-finder
  config.yaml, .env                   Linux:   ~/.local/share/singbox-subs-finder
  config/subs/urls.json               список ссылок на подписки
  config/templates/*.json             шаблоны конфигурации для деплоя
  config/reachability_targets.json    цели проверки reachability
  source/servers.db                   центральная база
  source/whitelist.txt, merge.txt     выгрузки
  source/downloaded/                  скачанные подписки
  logs/                               логи
  output/                             результат локального деплоя

<каталог программы>/                  Windows: %ProgramFiles%\singbox-subs-finder
  start.py, requirements.txt          Linux:   /opt/singbox-subs-finder
  singbox-subscribe/                  ПАКЕТ: только код
  .venv/                              окружение (в данных, если нет прав записи)
```

Смысл разделения: программу можно обновлять и переустанавливать, не задевая
файлы пользователя, а сами файлы видно сразу и не надо искать их внутри кода.
Пути в `config.yaml` записываются **относительно каталога данных** —
`config/templates`, а не `singbox-subscribe/config/templates`.

Относительные пути, ведущие внутрь пакета (например `urltest_template`),
считаются от **корня пакета**, а не от данных: шаблоны проверок приезжают
вместе с программой и меняются только вместе с ней.

**Старая установка из клона репозитория продолжает работать**: если рядом с
пакетом есть `config.yaml`, каталогом данных считается сам клон. Каталоги
задаются переменными `SINGBOX_PROGRAM_DIR` и `SINGBOX_DATA_DIR`.

## sing-box

Готовые бинарники лежат в пакете: `singbox-subscribe/sing-box/sing-box` (Linux)
и `singbox-subscribe/sing-box/sing-box.exe` (Windows).

Путь задаётся настройкой `singbox.path` в `config.yaml`. Принимается и папка
поставки, и файл напрямую: если указать каталог, бинарник найдётся внутри сам.
По умолчанию — папка поставки в пакете.

## Деплой

Собранный конфиг можно никуда не публиковать (`deploy.enabled: false` по
умолчанию), писать в файл на этой машине или пушить в GitHub:

```yaml
deploy:
  enabled: true
  local: true                # писать файл на диск — токены не нужны
  local_path: output

  # и/или в GitHub:
  repo: ваш-логин/ваш-репозиторий
  template: sbc-1.14.json    # шаблон из config/templates
  path: config.json          # путь файла внутри репозитория
```

Можно включить оба способа сразу: конфиг соберётся один раз и уйдёт и на диск,
и в репозиторий. Мульти-режим (`templates: [all]`) собирает по файлу на каждый
шаблон из `config/templates/`.

Репозиторий и источник IP по умолчанию пусты — это данные конкретной установки,
осмысленного умолчания у них нет. Когда деплой включён, а они не заполнены,
`preflight` скажет об этом прямо.

Ручной запуск деплоя:

```bash
cd singbox-subscribe
python deploy_config.py --templates all --local    # в файл, без токенов
python deploy_config.py --template sbc-1.14.json   # в GitHub
python deploy_config.py --list-templates           # что вообще есть
```
