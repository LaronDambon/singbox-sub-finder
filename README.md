## Введение
- Собирает списки серверов из источников в `config/subs/urls.json`.
- Объединяет, очищает и генерирует `source/merge.txt`.
- Запускает `urltest` через `sing-box`; результат (`stable`) пишется в центральную базу `source/servers.db` (SQLite).
- **Whitelist** (`whitelist.txt`, `/api/whitelist`) — серверы, пинговавшиеся в ПОСЛЕДНЕЙ проверке (`available=1`): пинганулся → добавляется в список, не пинганулся → не добавляется.
- **«Щит» от удаления**: сервер, пинговавшийся хотя бы раз (`ever_pinged=1`), защищён от удаления на `SHIELD_CYCLES=96` проверок. Каждый успех ставит `stable` не ниже `96`, каждая неудача списывает `1`.
- Новый сервер до первого удачного пинга имеет `stable=NEW_SERVER_STABLE=5`. Нижний порог `stable` — `0`: в проверку попадают **все** серверы со `stable >= 0`; дойдя до `-1`, сервер больше не импортируется из базы.
- Первая полная проверка будет долгой (200к+ серверов). Далее мёртвые серверы выпадают из пула проверки и поиск рабочих конфигов идёт значительно быстрее.
- Отфильтрованные сервера сохраняются в `source/whitelist.txt`, их можно использовать в любом клиенте без генерации конфига для sing-box.
- Либо можно сразу же собрать автономный конфиг для запуска sing-box.

## Архитектура: ядро pipeline

Вся логика проверки серверов вынесена в пакет `singbox-subscribe/pipeline/`.
`main.py` — тонкая точка входа: он только загружает ядро и вызывает его функции.

```
main.py                     загружает ядро и запускает прогон (логики проверки нет)
pipeline/
├── engine.py               движок: запускает этапы и гоняет их по расписанию
├── database.py             асинхронный доступ к БД + очередь проверки check_queue
├── context.py              общий контекст прогона (настройки, база, чекеры)
├── logging_setup.py        единое логирование (уровни, ротация, очистка)
├── dispatcher.py           СЛУЖБА 1: набор из базы + параллельные батчи
├── singbox.py              запуск батча: свой конфиг, свой порт, свой дедлайн
├── collector.py            СЛУЖБА 2: разбор вывода sing-box на лету
├── batch.py                как режем на батчи, как батч закончился
├── checkers/
│   ├── base.py             контракт Checker: CheckContext/CheckOutcome/CheckResult
│   ├── registry.py         автозагрузка чекеров из папок, выбор по PIPELINE_CHECKERS
│   ├── builtin/            штатные алгоритмы (обновляются с репозиторием)
│   │   ├── url_probe.py    urltest sing-box — РЕШАЕТ, жив ли сервер
│   │   ├── country.py      страна (эмодзи) для серверов без известной страны
│   │   ├── reachability.py профиль целевых сайтов -> тэги [name] / [Global]
│   │   └── speed.py        скорость МБ/с + доступ к сайту -> тэг [speed-*]
│   └── custom/             СВОИ алгоритмы: положите .py — он подхватится сам
└── stages/
    ├── discovery.py        поиск новых серверов из ссылок (расширяет БД)
    ├── check.py            воркеры: берут батчи из очереди, гоняют чекеры
    ├── writer.py           результаты чекеров -> записи в базу
    └── export.py           purge, whitelist/blacklist, merge.txt, деплой
```

Как проходит один прогон:

```
┌──────────────┐   upsert + enqueue   ┌───────────────┐
│  discovery   │ ───────────────────► │ check_queue   │  очередь В БАЗЕ,
│ (поиск по    │   refill_from_pool   │  (pending →   │  переживает перезапуск
│  подпискам)  │ ───────────────────► │  in_progress  │
└──────────────┘                      └───────┬───────┘
                                               │ claim_batch
                                        ┌──────▼───────┐
                                        │  check × N   │ воркеры, каждый со
                                        │ (батчи)      │ своим sing-box
                                        └──────┬───────┘
                                               │ record_results
                                        ┌──────▼───────┐
                                        │    export    │ purge + списки + деплой
                                        └──────────────┘
```

Поиск и проверка идут **одновременно**: как только база пополнилась новыми
серверами, воркеры уже берут их в работу. Очередь лежит в базе, а не в памяти,
поэтому перезапуск посреди прогона не теряет серверы, а состояние видно через
CLI и HTTP API.

### Свой проверяющий алгоритм

Файл с классом-наследником `Checker` в папке `pipeline/checkers/custom/`
подхватывается автоматически — ядро править не нужно. Заготовка уже лежит
рядом: [example_tcp_port.py](singbox-subscribe/pipeline/checkers/custom/example_tcp_port.py).

```python
from pipeline.checkers import CheckOutcome, CheckResult, Checker

class MyChecker(Checker):
    name = "my_checker"            # как включать в PIPELINE_CHECKERS
    description = "Моя проверка"
    decides_availability = True    # этот чекер решает, жив ли сервер

    async def check(self, ctx: CheckResult):      # -> CheckResult
        outcomes = {}
        for line in ctx.lines:
            ok, ping = await ctx.run_sync(my_probe, line)   # блокирующий код -> в поток
            outcomes[line] = CheckOutcome(ok=ok, ping_ms=ping)
        return CheckResult(outcomes=outcomes)
```

### Две службы проверки

**Служба 1 — диспетчер.** Забирает серверы из базы по фильтрам и режет список на
**параллельные** батчи. Полный батч — `PIPELINE_BATCH_SIZE` (100). Остаток не
гоняется одним недобранным батчем, а дробится между свободными слотами:

| серверов | батч | параллельных процессов | разбиение |
|---|---|---|---|
| 131 | 100 | 3 | `100 + 15 + 16` |
| 30 | 100 | 3 | `10 + 10 + 10` |
| 133 | 100 | 2 | `100 + 33` |

У каждого батча **свой** конфиг-файл, **свой** свободный inbound-порт и **свой**
дедлайн, посчитанный по размеру: большой батч живёт дольше мелкого, но мелкий
нельзя убивать по таймауту большого. Процессы идут действительно одновременно —
на последнем прогоне батч из 33 отработал за 36 с, пока батч из 100 ещё шёл
101 с, и всё вместе заняло 101 с вместо 137.

**Служба 2 — сборщик ответа.** Читает вывод каждого запущенного sing-box
построчно, **не дожидаясь конца запуска**. Если батч убили по таймауту, всё, что
sing-box успел напечатать, уже разобрано и попадёт в базу: 15 ответов из 30 не
теряются, а оставшиеся 15 уйдут в повтор.

### Три состояния сервера

Раньше было два: «жив» и «мёртв». Ответов от sing-box на все серверы батча не
приходит — часть просто молчит. Молчание раньше считалось смертью, и сбой одного
батча выглядел как массовая гибель. Теперь состояний три:

| состояние | что означает | что с сервером |
|---|---|---|
| `ALIVE` | sing-box ответил `available` | `available=1`, пинг, `stable` растёт |
| `DEAD` | sing-box ответил `unavailable` | `available=0`, `stable` падает |
| `NO_RESULT` | sing-box не упомянул сервер **вообще** | ничего не пишем, возврат в очередь |

`NO_RESULT` — это таймаут батча, сбой сборки конфига или обрыв связи с
процессом. Такой сервер **не выписывается**, а просто проверяется ещё раз. Чтобы
круг не стал вечным, число попыток хранится в очереди (`attempts`): после
`PIPELINE_MAX_RETRIES` сервер снимается с проверки на этот прогон.

### Про скорость: баты живут недолго

sing-box не отдаст вердикт по серверу быстрее, чем сервер ответит, поэтому
затянувшийся батч **убивается по своему дедлайну**, а не доводится до конца:

| параметр | по умолчанию | что это |
|---|---|---|
| `PIPELINE_CHECK_TIMEOUT` | 20 с | доля размера батча в дедлайне |
| `PIPELINE_BATCH_STARTUP` | 10 с | постоянная часть: старт процесса, разбор конфига, DNS |
| `PIPELINE_MAX_RETRIES` | 3 | сколько кругов повтора до снятия с проверки |
| `PIPELINE_ENRICH_TIMEOUT` | 180 с | отдельные часы для чекеров-дополнений |

Итоговый дедлайн батча = `PIPELINE_BATCH_STARTUP + PIPELINE_CHECK_TIMEOUT × размер/100`.
Батч из 100 живёт 30 с, осколок из 22 — 15 с.

Так проверка идёт кругами, и это нормально: первый круг отвечает быстрыми
серверами, второй и третий добирают тех, кто не успел. На прогоне 133 серверов
круги шли так — `133 → 79 → 44 → 28 снято`, и суммарно sing-box работал меньше
минуты. Серверы, которым не ответил ни один круг, честно помечаются как «не
получено ни одного вердикта», а не как мёртвые.

### Сбой конфига — это не «серверы мёртвые»

Если батч не собрался, он делится **пополам**, чтобы найти кривую строку:
нерабочие батчи не трогаются. Различаются:

| исход | что делаем |
|---|---|
| `COMPLETED` | все ответили |
| `PARTIAL` | часть ответила, остальные в очередь |
| `NO_RESULTS` | sing-box отработал, ни одного вердикта |
| `CONFIG_ERROR` | не собрался конфиг — делим пополам, ищем кривую строку |
| `SPAWN_ERROR` | процесс не запустился — повтор на другом порту |

Отдельная страховка: если неразбираемыми оказались почти все строки батча, это
почти наверняка поломка разбора ссылок, а не битые ссылки — такой набор
**не уходит в чёрный список**, а возвращается в очередь.

Два вида чекеров:

| вид | `decides_availability` | что делает |
|---|---|---|
| решающий | `True` | даёт `ok`/`ping`; его вердикт пишется в базу как `available` |
| дополнение | `False` | только обогащает результат (`country`, `capabilities`); `ok=None` |

Чекеры-дополнения запускаются **только на выживших серверах** (если не задан
`run_on_dead = True`), поэтому страна, reachability и speed не тратят sing-box на мёртвые.

Тэги из разных дополнений **складываются**, а не затирают друг друга: сервер
может получить и `[gemini]`, и `[speed-fast]` одновременно.

Включить свой чекер — одна переменная:

```bash
PIPELINE_CHECKERS=url_probe,my_checker
```

### Проверка скорости

`speed` — дополнение, которое меряет настоящую пропускную способность сервера
и заодно проверяет, открывается ли через него целевой сайт. Пинг для этого
показателен плохо: до Gemini пинг есть, а страницу сервер не отдаёт.

Каждый сервер проверяется в два шага, оба через один локальный порт sing-box:

1. **Сайт** (по умолчанию `gemini.google.com`) — короткий таймаут и первые
   килобайты. Дальше ищем признаки блокировки: код 401/403/429/451/503,
   редирект на `accounts.google.com`, капча или «unusual traffic» в теле.
2. **Скорость** — выкачка с `speed.cloudflare.com/__down?bytes=N`, которая
   отдаёт ровно запрошенное число байт, и пересчёт в МБ/с.

Два решения, ради которых проверка остаётся экономной:

* ограничение **по времени чтения, а не по размеру** — медленный сервер
  отдаёт столько, сколько успел за `SPEED_READ_SECONDS`, и уходит, не
  выкачивая мегабайты впустую;
* **сайт и скорость не зависят друг от друга** — недоступный Gemini не
  отменяет замер пропускной способности, он лишь ставит метку `[speed-blocked]`
  или `unknown`.

| переменная | по умолчанию | смысл |
|---|---|---|
| `SPEED_ENABLED` | `1` | включать ли чекер |
| `SPEED_SITE_URL` | `https://gemini.google.com/` | сайт для проверки доступа |
| `SPEED_PROBE_URL` | `https://speed.cloudflare.com/__down` | источник данных для замера |
| `SPEED_PROBE_BYTES` | `4194304` | сколько байт запрашивать (4 МБ) |
| `SPEED_READ_SECONDS` | `4.0` | потолок ЧТЕНИЯ, а не размера |
| `SPEED_MIN_MBPS` | `1.0` | ниже — `speed-slow` |
| `SPEED_GOOD_MBPS` | `5.0` | от этого и выше — `speed-fast` |

Итог пишется тэгом в `capabilities` (`[speed-fast]`, `[speed-ok]`,
`[speed-slow]`, `[speed-blocked]`) и полными числами в отчёт. Транспорт общий
с проверкой достижимости — [script/proxy_probe.py](singbox-subscribe/script/proxy_probe.py),
поэтому логика поднятия sing-box существует в репозитории один раз.

### Команды ядра

Запускаются **из папки `singbox-subscribe/`** (как и `python -m script.server_store`):

```bash
cd singbox-subscribe

python -m pipeline run       # полный прогон: поиск -> очередь -> проверка -> экспорт
python -m pipeline serve     # режим служб: всё крутится постоянно (см. ниже)
python -m pipeline check     # только проверка (очередь наполняется из базы)
python -m pipeline discover  # только поиск новых серверов из подписок
python -m pipeline export    # только экспорт списков из базы
python -m pipeline checkers  # какие проверяющие алгоритмы доступны
python -m pipeline status    # состояние базы и очереди (JSON)
python -m pipeline queue     # счётчики очереди (JSON)
python -m pipeline logs      # где лежат логи и сколько они занимают
```

### Режим служб

`python -m pipeline serve` поднимает те же этапы, что и `run`, но не по
очереди, а одновременно и постоянно. Каждая служба — отдельный бесконечный
цикл со своим интервалом, и общаются они **только через очереди в базе**:

```
discovery  --(нашёл серверы)-->  check_queue
collector  --(добрал из базы)--->  check_queue
checker    --(взял батч)------>  result_queue
results    <--(забрал вердикты)-  result_queue  --> запись в servers
publisher  <--(раз в N минут)--  servers  --> whitelist/merge/деплой
```

Обычный прогон строго последователен: поиск, потом очередь, потом проверка,
потом экспорт. Каждый шаг ждёт предыдущий, между шагами система простаивает,
а свежие серверы ждут своей очереди. Службы устроены иначе — **ни одна служба
не ждёт окончания другой**: `discovery` может докладывать серверы в очередь,
пока `checker` уже гоняет батчи, а `publisher` выгружать свежие результаты, не
дожидаясь, пока опустеет очередь проверки. Порядок запуска не важен: службы не
вызывают друг друга и не знают о существовании остальных.

| служба | что делает | интервал по умолчанию |
|---|---|---|
| `discovery` | скачивает подписки и кладёт найденные серверы в очередь проверки | `SERVICE_DISCOVERY_INTERVAL` = 3600 с (час) |
| `collector` | достаёт из таблицы серверов записи (`excluded=0`, `stable` не ниже порога) и ставит их в очередь | `SERVICE_COLLECTOR_INTERVAL` = 60 с |
| `checker` | берёт батчи из очереди и гоняет sing-box; вердикты в базу не пишет, а кладёт в `result_queue` | без пауз — работает, пока очередь не опустеет |
| `results` | забирает порции вердиктов из `result_queue` и переносит их в таблицу серверов | `SERVICE_RESULTS_INTERVAL` = 2 с |
| `publisher` | обновляет whitelist/blacklist/merge свежими рабочими серверами; деплой по расписанию выключен | `SERVICE_PUBLISHER_INTERVAL` = 1800 с (полчаса) |

Значения по умолчанию — из
[singbox-subscribe/config/settings.py](singbox-subscribe/config/settings.py). У `checker`
интервала нет вовсе (`SERVICE_CHECKER_INTERVAL` в env.py не существует): служба
крутится без остановки и лишь ждёт, когда очередь опустеет; настраивают её
общие `PIPELINE_BATCH_SIZE`, `PIPELINE_CHECK_WORKERS` и `PIPELINE_CHECKERS`.

Запуск:

```bash
python -m pipeline serve                  # крутится, пока не остановят (Ctrl+C)
python -m pipeline serve --duration 120   # отработать 120 секунд и выйти
```

`--duration` — это секунды (`--duration 3600` = час); нужен для проверки и
тестов, чтобы не держать службы надолго. Ещё у команды есть `--checkers`,
а общий путь к базе задаётся **до** имени команды:
`python -m pipeline --db source/servers.db serve`.

За службами следит `Supervisor`
([pipeline/services/base.py](singbox-subscribe/pipeline/services/base.py)):
упавшая не убивает процесс — к ней применяется отложенный повтор (2 с, потом
×2, но не дольше 120 с), раз в минуту печатается сводка (проходы, ошибки,
последняя ошибка), а по Ctrl+C всем даётся 20 секус дописать последний батч и
применить вердикты, которые уже лежат в очереди результатов.

**Осторожно: в режиме служб вердикты сначала попадают в `result_queue`, и в
таблицу серверов их переносит отдельная служба.** `checker` только считает —
вердикт считается, когда sing-box ответил, — а перенос в `servers` делает
`results`. Если она выключена (`SERVICE_RESULTS=0`) или упала, очередь
результатов будет расти, а серверы останутся неподтверждёнными: `stable` не
изменится, и в `whitelist.txt` они не попадут, пока очередь не разберётся.

Обычный `python -m pipeline run` работает как раньше: он по-прежнему
последовательный, а вердикты пишет в базу сразу (`DirectSink`), без очереди
результатов. Ничего не изменилось — режим служб включается только явной
командой `serve`.

### Запуск: всё по-старому

```bash
python start.py              # API + планировщик запуска main.py
```

`start.py` менять не пришлось: он по-прежнему поднимает `gensub_api.py` и
периодически запускает `singbox-subscribe/main.py` из корня репозитория —
новый `main.py` сам добавляет свою папку в `sys.path`, поэтому `cwd` не важен.
Один запуск `main.py` = один полный цикл (по умолчанию процесс завершается,
`start.py` поднимет его снова). Если нужен непрерывный цикл без перезапуска
процесса:

```bash
python singbox-subscribe/main.py --interval 1800   # цикл каждые 30 минут
```

### Логирование

Один модуль на весь проект: `pipeline/logging_setup.py`. Любая точка кода берёт
логгер одной строкой и получает уже настроенные обработчики:

```python
from pipeline.logging_setup import get_logger

LOGGER = get_logger(__name__)     # имя модуля попадает в запись
LOGGER.info("Сервер %s жив, пинг %s мс", name, ping)
```

Главное правило: **`LOG_LEVEL` — это порог.** Запись ниже порога не попадает
ни в один файл и ни в консоль:

| `LOG_LEVEL` | что попадает в логи |
|---|---|
| `DEBUG` | всё, включая отладочные сообщения |
| `INFO` | info, warning, error, critical |
| `WARNING` | warning, error, critical |
| `ERROR` | только error и critical |

Файлы устроены так, что запись **не копируется по четырём файлам**: главный
`app.log` хранит всё, что прошло порог, а per-level файлы содержат **только
свой уровень** (`info.log` — только INFO, и т.д.). Файлы ниже `LOG_LEVEL` не
создаются вовсе.

Настройки — в [singbox-subscribe/config/settings.py](singbox-subscribe/config/settings.py)
(раздел «ЛОГИРОВАНИЕ»), примеры в [`.env.example`](.env.example):
`LOG_LEVEL`, `LOG_CONSOLE_LEVEL` (уровень консоли отдельно от файлов),
`LOG_MAX_BYTES`/`LOG_BACKUP_COUNT` (ротация по размеру), `LOG_RETENTION_DAYS`
(удаление файлов старше N дней), `LOG_PER_LEVEL_FILES`, `LOG_FORMAT=text|json`,
`LOG_THROTTLE_LIMIT`/`LOG_THROTTLE_WINDOW` (защита от тысяч одинаковых строк).

## Фильтры при генерации конфига

Кроме старого `filter` (включить/исключить узлы по регулярке к **имени** узла)
в шаблоне можно указать ключ `server_filter` — он отбирает серверы по данным
**базы**: профилю доступности, стране, региону, задержке, stable и протоколу.
Это разные вещи: страна и профиль лежат в колонках `servers`, а в самой строке
подписки их может не быть вовсе, поэтому по имени их не отобрать.

```json
{
  "server_filter": {
    "capabilities": {"any": ["Global"], "none": ["speed-blocked"]},
    "exclude_countries": ["RU"],
    "max_ping_ms": 1500,
    "min_stable": 3
  }
}
```

Такой фильтр — это ровно «все серверы, у которых есть Global, кроме России».

Ключи `server_filter`:

| ключ | смысл |
|---|---|
| `capabilities` | объект `any` / `all` / `none` по тегам профиля |
| `include_countries` / `exclude_countries` | кодом (`RU`), флагом или названием (`Russia`, `Россия`) |
| `country_regions` / `exclude_country_regions` | `EU`, `ASIA`, `AMERICAS`, `AFRICA`, `OCEANIA`, `MIDDLE_EAST` |
| `min_stable` | минимальный счётчик жизней |
| `max_ping_ms` | максимальная задержка; серверы с **неизвестной** задержкой не проходят |
| `protocols` / `exclude_protocols` | `vless`, `trojan`, `vmess` и т.д. |
| `name_regex` / `exclude_name_regex` | регулярка по имени строки |
| `require_country` | `true` — оставить только серверы с известной страной |

Проверка строгая: неизвестный ключ, неизвестный регион, нераспознанная страна и
некомпилируемая регулярка **останавливают сборку** с внятным сообщением. Раньше
такая ошибка либо проходила молча (опечатка в ключе просто ничего не делала),
либо роняла всю сборку с `re.error` без указания, какой фильтр виноват.

Страна хранится в базе как эмодзи-флаг и заполнена у части серверов. У остальных
`country` пуст: `exclude_countries` их не тронет, а `require_country: true` отсеет.

Сборка конфига отказывается выполняться, если `route.final` или любое правило
маршрута указывает на группу **без участников**: sing-box такие группы считает
нормальными и молча не выпускает наружу трафик.

## Определение страны сервера (country_check)
Реализация по мотивам [Throne](https://github.com/throneproj/Throne) (core/server/test_utils/speedtest_utils.go):
- **один** процесс sing-box на батч прокси: каждому прокси — свой mixed-inbound на 127.0.0.1 и правило маршрутизации inbound → outbound, т.е. локальный порт жёстко привязан к своему конфигу (у Throne то же самое через outbound.DialContext в одном запущенном ядре);
- потоки Python параллельно стучатся в свои порты (COUNTRY_CHECK_CONCURRENCY, по умолчанию 8; в Throne — countryConcurrency=5);
- страна определяется одним лёгким запросом через цепочку: Cloudflare cdn-cgi/trace → api.ip.sb/geoip → ipinfo.io/json (вместо списка серверов speedtest.net, который блокирует датацентровые IP и давал ~40% отказов);
- ISO-код сразу превращается в эмодзи флага и пишется в базу (колонка country), поэтому повторных проверок для известных стран нет.

Если страна уже известна (эмодзи в имени или запись в базе) — сервер вообще не отправляется на проверку.

## Центральная база серверов (servers.db)
Единственный источник правды о серверах и их стабильности — SQLite-база `singbox-subscribe/source/servers.db` (модуль [script/server_store.py](singbox-subscribe/script/server_store.py), класс `ServerStore`).

При первом запуске база автоматически наполняется из старых `whitelist.txt`/`blacklist.txt` (whitelist-серверы считаются пинговавшимися и получают щит, blacklist — умершие).

Зоны stable (при настройках по умолчанию, порог `0`, мёртвый `-1`):

| Диапазон | Значение |
|---|---|
| `stable = -1` | умерший: не импортируется в проверку (`excluded=1` после purge) |
| `stable = 0` | на границе: одна неудачная проверка до смерти |
| `stable 1..95` | живёт за счёт остатка «щита» |
| `stable >= 96` | под полным щитом после удачного пинга; в whitelist по результату последней проверки (`available=1`) |

Пороги настраиваются переменными окружения:
- `PURGE_STABLE_BELOW` (по умолчанию `0`) — нижний порог: из проверки исключаются все со `stable <` порога (то есть умершие `stable=-1`);
- `NEW_SERVER_STABLE` (по умолчанию `5`) — stable нового сервера до первого удачного пинга;
- `SHIELD_CYCLES` (по умолчанию `96`) — «щит» после удачного пинга: минимум неудачных проверок, которые сервер переживёт.

### Принцип whitelist и «щит» от удаления (stable)
- **Whitelist = последняя проверка.** Принципа «2 раза не пинганулся — убрать из
  whitelist» больше нет: сервер пинганулся → добавляется в whitelist
  (`whitelist.txt`, `/api/whitelist`, деплой), не пинганулся → не добавляется.
  На следующем цикле он снова проверяется, и список обновляется целиком.
- **«Щит» для пинговавшихся.** В базе есть колонка `ever_pinged` (1 — сервер
  пинговался хотя бы раз). Каждый удачный пинг ставит `stable` не ниже
  `SHIELD_CYCLES=96`: сервер переживёт до 96 неудачных проверок подряд. Каждая
  неудача списывает `-1`, поэтому сервер со щитом постепенно «истекает».
- **Новый сервер** до первого удачного пинга имеет `NEW_SERVER_STABLE=5`:
  несколько попыток доказать жизнеспособность.
- **Мёртвый порог — `0`.** В цикл проверки импортируются все серверы со
  `stable >= PURGE_STABLE_BELOW=0` (`check_pool`); дойдя до `-1`, сервер больше
  не импортируется из базы. `stats()`/лог цикла показывают зоны
  `alive`/`dead`/`shielded`/`online`/`reserve`/`unchecked`.
- Колонки старой модели (`fail_streak`, `temp_ban_until`, `countries`,
  `dirty_tags`) больше не используются; старая база мигрирует автоматически
  (маркеры `servers.tempban-migrated.json`, `servers.shield-migrated.json`).

CLI управления базой (из папки `singbox-subscribe`):

```bash
python -m script.server_store stats                 # статистика по зонам stable
python -m script.server_store export                # whitelist: пинговавшиеся в последней проверке (available=1)
python -m script.server_store export --min-stable 1 # вывести список stable > 1
python -m script.server_store export --max-stable 0  # вывести умерших (stable < 0)
python -m script.server_store purge --below 0        # исключить умерших из проверки (--hard — удалить физически)
python -m script.server_store reset-excluded         # вернуть исключённые в ротацию (сброс состояния)
```

HTTP API (дополнительно к `/api/whitelist`, который теперь читает базу):
- `GET /api/servers/stats` — статистика базы;
- `GET /api/servers?available=1` — whitelist (пинговавшиеся в последней проверке); `?min_stable=1` — выборка `stable > 1`; `?max_stable=0` — `stable < 0` (умершие, не импортируются); поддержан `limit`.

## Автозапуск (Linux)
- Для непрерывной работы можно добавить системный unit (systemd) или cron, который запускает `start.py`.

Пример systemd unit (создайте `/etc/systemd/system/singbox-sub-finder.service`):

```bash
sudo nano /etc/systemd/system/singbox-subscribe.service
```
Вставьте следующее, и ОБЯЗАТЕЛЬНО замените USER на свой.

```ini
[Unit]
Description=Sing-box subscribe runner
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=USER
WorkingDirectory=/home/USER/singbox-sub-finder
ExecStart=/home/USER/singbox-sub-finder/.venv/bin/python start.py
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
```

После создания:

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now singbox-sub-finder
```

## Проблемы при запуске sing-box
- При запуске `sing-box` возможны следующие распространённые проблемы:
	- неверная архитектура/платформа бинарника (Windows `.exe` не запустится в Linux);
	- отсутствие права на исполнение у файла (`chmod +x sing-box` на Linux);
	- порт, который использует `sing-box`, может быть заблокирован фаерволлом. Для Ubuntu с `ufw` откройте порт, который вы используете, например:

```bash
sudo ufw allow <PORT>/tcp
```

	- если `sing-box` должен слушать привилегированный порт (<1024), убедитесь, что запуск идёт от пользователя с нужными правами.

Если понадобятся подсказки по диагностике ошибок запуска — пришлите вывод консоли или логи из `logs/`.
