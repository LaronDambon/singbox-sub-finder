# Changelog

Все заметные изменения проекта документируются в этом файле.
Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/),
версионирование — [Semantic Versioning](https://semver.org/lang/ru/).
## [3.0.0] — 2026-11-06

Первый релиз с установщиком. Главное изменение — **настройки переехали из
`.env` в человеческий `config.yaml`**, а рабочие файлы отделены от кода.
Обновление поверх 2.x поддерживается: старый `.env` не ломает установку.

### Added

- **Установка, обновление и мастер настройки.** Три команды, по обёртке на
  каждую ОС; логика общая и лежит в `installer.py` / `setup.py`:

  ```bash
  ./install.sh      # или .\install.ps1      — установка с нуля
  ./update.sh       # или .\update.ps1       — обновление
  ./setup.sh        # или .\setup.ps1        — мастер настройки
  ```

  Обёртки намеренно тонкие: находят Python, передают аргументы и зовут общий
  модуль. Иначе установка на Windows и Linux разошлась бы на первом же шаге.

- **Загрузчик одной командой.** Клонировать вручную не нужно:

  ```bash
  curl -fsSL https://raw.githubusercontent.com/LaronDambon/singbox-sub-finder/main/bootstrap.sh | bash
  ```
  ```powershell
  irm https://raw.githubusercontent.com/LaronDambon/singbox-sub-finder/main/bootstrap.ps1 | iex
  ```

  Скачивает репозиторий и запускает установку. Повторный запуск обновляет
  существующую установку, не затирая `config.yaml`, `.env` и базу.

- **Мастер настройки спрашивает только то, что нельзя решить за человека:**
  какие чекеры запускать, есть ли ключи для проверки сервисов, куда девать
  собранный конфиг. Ответы пишутся в `config.yaml` и `.env`; комментарии в
  `config.yaml` сохраняются (через `ruamel.yaml`, а не обычный дамп).

- **`preflight.py` — проверка готовности до запуска.** Раньше настройка не
  соответствовала запуску, и узнавалось это сильно позже: по пустому
  `whitelist.txt`, по метке, которой нет, по молча не сработавшему деплою.
  Теперь те же условия проверяются до старта, и на каждую неудачу выдаётся
  инструкция — как добавить или как выключить. Запуск не блокируется:
  `start.py` делает проверку при каждом старте (`PREFLIGHT=off` отключает),
  `--strict` делает ошибки фатальными.

- **Локальный деплой (`deploy.local`).** Собранный конфиг можно писать файлом
  на этой машине, без репозитория и **без единого токена**. Раньше выбор был
  только «в GitHub или никуда», хотя собранный конфиг нужен всем. Режимы
  складываются: `local` и `repo` можно включить одновременно, конфиг
  соберётся один раз и уйдёт в оба места.

- **`python -m pipeline config init|show|export`.** `init` создаёт
  `config.yaml` с комментариями, `show` печатает действующие значения с
  указанием источника каждого и маскирует секреты, `export` выводит шаблон.

- **`config/config.py` — схема настроек.** Единственное место, где настройка
  определена: группа в YAML, ключ, тип, умолчание, описание, единица
  измерения, признак секрета. Из неё выводятся и разбор конфига, и
  сгенерированный файл, и таблица старых имён.

- **Документация разделена.** `README.md` — короткая инструкция по запуску,
  `docs/` — подробное описание: архитектура, настройки, проверки, база,
  деплой, разбор проблем.

### Changed

- **Настройки: из «`.env` + settings.py» в `config.yaml`.** Раньше у настройки
  было только имя: `REACHABILITY_MAX_PING_MS=500` не говорил ни что это, ни в
  чём измеряется, ни какие значения допустимы. Теперь настройки описаны схемой
  и сгруппированы по инструментам:

  ```yaml
  singbox:
    checkers:
      reachability:
        urls_file: config/reachability_targets.json
        max_ping_ms: 500
        concurrency: 8
  ```

  Группа — это инструмент: настройки одного чекера лежат в
  `singbox.checkers.<имя>`, общее ядро — в `singbox`.

- **Приоритет слоёв: CLI → системное окружение → `config.yaml` → умолчания
  схемы.** `config.yaml` стоит ВЫШЕ окружения, поэтому переменная с прежним
  именем из `.env` больше не перебивает файл.

- **`.env` — только секреты.** Четыре переменные: `GH_DEPLOY_TOKEN`,
  `GH_READ_TOKEN`, `GEMINI_API_KEY`, `OPENROUTER_API_KEY`. Обычные настройки
  оттуда НЕ читаются. `.env.example` сокращён с 346 строк (73 имени) до 39
  строк — иначе шаблон сам учил складывать в `.env` то, чему там не место.

- **Умолчание чекеров — `url_probe, reachability, api_service,
  browser_service`.** `country`, `service_access` и `speed` остаются
  доступными: их достаточно вписать в `singbox.enabled_checkers`, но по
  умолчанию они не тратят время.

- **Рабочие файлы отделены от кода.** Пакет `singbox-subscribe/` содержит
  ТОЛЬКО исполняемый код, а всё, что пользователь правит или накапливает,
  лежит рядом с ним, в корне репозитория:

  | Было (внутри пакета) | Стало (в корне) |
  | --- | --- |
  | `singbox-subscribe/config/templates/` | `config/templates/` |
  | `singbox-subscribe/config/subs/` | `config/subs/` |
  | `singbox-subscribe/config/reachability_targets.json` | `config/reachability_targets.json` |
  | `singbox-subscribe/source/` | `source/` |
  | `singbox-subscribe/logs/` | `logs/` |
  | `singbox-subscribe/output/` | `output/` |
  | `browser.py` (в корне) | `singbox-subscribe/browser.py` |

  Пути в `config.yaml` записываются **относительно корня репозитория**
  (`config/templates`, а не `singbox-subscribe/config/templates`). Смысл:
  пакет можно обновлять, не задевая файлы пользователя, а сами файлы видно
  сразу. `browser.py` переехал ВНУТРЬ пакета — он часть программы.

- **`repo` и `ip_source` по умолчанию пусты.** Это данные конкретной
  установки; чужой репозиторий и путь `/home/ray/...` выглядели рабочими
  настройками и вели в никуда. Когда деплой включён, а они не заполнены,
  `preflight` скажет об этом прямо.

- **Шаблон: служебный ключ `alldeploy` вместо пары блоков-заглушек.** В
  `outbounds` шаблона теперь лежит один контейнер, который размножается на
  метки сервисов:

  ```json
  {
    "tag": "alldeploy",
    "type": "block",
    "tags": ["all"],
    "blocks": [
      { "tag": "alldeploy-reserved", "type": "urltest",
        "filter": [ {"action": "include", "keywords": ["alldeploy-reserve"]} ] },
      { "tag": "alldeploy", "type": "urltest",
        "outbounds": ["{all}", "alldeploy-reserved"],
        "filter": [ {"action": "include", "keywords": ["alldeploy-best"]} ] },
      { "tag": "alldeploy-best", "type": "urltest",
        "filter": [ {"action": "include", "keywords": ["alldeploy-best"]} ] }
    ]
  }
  ```

  `tags` решает, на какие метки размножать: `["all"]` — все метки из
  `reachability_targets.json` плюс браузерная метка; явный список — только
  перечисленные. Подстановка идёт **до** фильтрации, поэтому фильтр ищет по
  уже подставленному имени: в группу попадают только строки с меткой
  `<метка>-best`, а не всё, что совпало подстрокой. Служебный контейнер в
  собранный конфиг не попадает.

- **Три суффикса разведены: `-best`, `-reserve` и `-reserved`.** Метка в
  базе — `<метка>-reserve`, имя группы — `<метка>-reserved`. Раньше оба
  звались одинаково, и фильтр резерва ловил метку подстрокой.

- **Сервис без лучших серверов не создаётся вообще.** Нет группы
  `<метка>-best` — нет ни `<метка>`, ни `<метка>-best`, ни
  `<метка>-reserved`, ни правила маршрута. Правило в несуществующую группу
  удаляется, а не переводится в `proxy`: перевод означал бы, что трафик
  сервиса молча уходит в общий контур, и снаружи это выглядит как работающий
  сервис.

- **Группа merge — это просто имя, а не «Global».** `list` группы читается
  как есть и может содержать не только цели, но и метки уровней
  (`["gstatic", "yandex-reserve", "cloudflared-best"]`). Среднее считается по
  всем элементам списка: сервер хорош для группы, только если отвечает по
  всем её точкам сразу. Прежний минимум по трём захардкоженным целям давал
  серверу `Global=390` при целях `1359/1203/390`.

- **Профиль тегов пишется по проходам, а не копится историей.** Списки
  «какие метки вытеснять» (`capabilities_replace` / `capabilities_clear`)
  убраны совсем: они разошлись с реальностью — у каждой категории был свой
  набор, никто не мог сказать, чей тег лежит в базе, и метка, снятая у всех
  серверов, оставалась висеть мусором. Теперь проход нумеруется меткой
  (`capabilities_pass`), в начале прохода признак «профиль записан» снимается
  у всех, **первый** ответивший по серверу чекер пишет профиль сбросом, а
  остальные (`api_service`, `browser_service`, `speed`) только дописывают.
  Сброс делает именно первый ответивший, а не конкретно `reachability`:
  выключенный чекер больше не оставляет сервер без перезаписи профиля.

- **Мёртвому серверу стирается весь профиль тегов.** Раньше снимались только
  метки из списка «категорий сервисов», и метка, которой в списке не
  оказалось, жила на мёртвом сервере навсегда.

### Fixed

- **`api_service` и `browser_service` больше не считаются дублями.**
  Предупреждение убрано как фактически неверное: они проверяют разные точки,
  и у Google разная политика и разная доступность этих точек. Обе проверки
  законны и ставят разные метки — `gemini-api` и `gemini-chat`.

- **`export.py` падал на списке шаблонов.** `deploy.templates` приходит и
  списком (так его пишет `config.yaml`), и строкой через запятую (старая форма
  из `.env`); код ждал только строку и ронял прогон на `list.replace`.
  Теперь обе формы принимаются — в `export.py` и в `deploy_config.py`.

- **`check_local_deploy` и `check_ip_source`.** Локальный деплой проверяет,
  что каталог существует и доступен на запись (иначе конфиг молча не
  появится); источник IP требуется, только если шаблон реально содержит
  плейсхолдер — иначе проверка придиралась бы к рабочей настройке.

- **`discovery` искал `downloaded/` отсчётом уровней.** Путь считался как
  «три уровня вверх от `urls.json`» и был привязан к тому, что файл лежит
  внутри пакета. После переезда рабочих файлов он указывал в никуда. Теперь
  каталог берётся от пути базы.

- **`preflight` неверно разрешал путь к бинарнику.** Своя арифметика
  расходилась с рабочим кодом: `sing-box.exe` искался в корне репозитория,
  а конвейер брал его из пакета, и годная установка получала ложную ошибку.
  Теперь зовётся та же функция `resolve_binary`.

- **`.gitignore` не игнорировал `.env`.** В строках `.env `, `.venv ` и ещё
  пяти были хвостовые пробелы — git читал их как имена с пробелом, то есть
  правило не работало. Пробелы убраны, `source/`, `logs/`, `output/`,
  `config.yaml` приведены к новой раскладке.

- **`config export` замораживал живые значения.** Голый `render_config()`
  сбрасывал 9 настроек к умолчаниям схемы. Теперь файл генерируется из
  действующего конфига.

- **Пути и уровни писались в `config.yaml` машинозависимо:** `singbox.path`
  уезжал абсолютным путём этой машины (`kind == "binary"` не попал в ветку
  относительных путей), а `log.level` — числом `20` вместо `INFO`.

### Compatibility

- **Обновление поверх 2.x ничего не ломает.** `.env` продолжает читаться как
  источник секретов, а старые имена настроек разбираются по таблице
  `_FIELD_MOVES`. Если в вашем `.env` остались строки вида
  `PIPELINE_CHECKERS=...` или `LOG_LEVEL=...` — они больше ничего не
  переключают, их можно удалить.

- **Старый код не правился.** `get_settings().reach.global_tag`,
  `s.pipeline.checkers` и `s["url_probe.batch_size"]` работают: у групп есть
  и историческое имя, и имя инструмента, а переехавшие поля перенаправляются
  таблицей `_FIELD_MOVES`.

### Verified

- `preflight` — 14/14 проверок на чистой установке.
- Все модули компилируются и импортируются; `config.yaml` прочитан.
- База читается из `source/servers.db` (2871 сервер), логи пишутся в `logs/`.
- Локальный деплой собран end-to-end: 27 629 байт, 31 outbound.
- `start.py` поднимается целиком: preflight, Flask API, конвейер с чекерами.
- Слои проверены по очереди; секреты не попадают в `as_dict()` и маскируются
  в `describe()`.

## [2.9.0]

### Added
- **API-проверка сервисов (`api_service`) — тот же тест, что и браузерный,
  но без браузера.** У Gemini и OpenRouter есть машинный ответ на запрос с
  ключом, и закрытый по региону сервис отвечает явной ошибкой: Gemini —
  `400 FAILED_PRECONDITION` «User location is not supported for the API use»,
  OpenRouter — `403` «Access denied by security policy». Раньше этот сигнал
  было видно только браузеру (анонимный HTTP-запрос получает лендинг и никогда
  заглушку — она рендерится клиентски после входа), поэтому проверка сервисов
  стоила запуска Chromium на каждый сервер.
  - Запросы **бесплатные** (метаданные модели, счёт моделей), токены не
    тратятся — проверка идёт по всей базе, а не по уже отобранным меткам.
  - Это **не третья логика, а тот же тест**: общий список сервисов, общий
    словарь вердиктов, общая таблица `service_bans` в `servers.db` и общий
    бренч (снятие метки сервиса). Браузер и API пишут в одни и те же строки и
    видят результаты друг друга: `checked_by` различает транспорт.
  - `PIPELINE_CHECKERS` по умолчанию теперь `url_probe,reachability,api_service`.
    `browser_service` не удалён — включается одной строкой, когда нужен именно
    браузер. Причина смены умолчания — цена: API отвечает за доли секунды,
    браузер занимает 3–20 с на сервер и требует сохранённой сессии.
- **Правила разбора ответа прямо в цели.** В `config/reachability_targets.json`
  у цели появился блок `api` с URL, заголовками и списком правил: первое
  совпавшее правило даёт вердикт (`ok`/`ban`/`unknown`). Правила пишутся
  плоской строкой (`{"verdict": "ban", "body_json_error_status": [...]}`) —
  прежняя форма с вложенным `if` тоже принимается. Запреты обязаны стоять
  **выше** разрешений, иначе `ban` не сработает на общем `200`.
  Условия: `status_in`, `body_contains`, `body_contains_all`,
  `body_not_contains`, `body_json_success`, `body_json_error_status`.
- **Ссылки на переменные окружения в целях: `$env:ИМЯ`.** Ключи доступа в
  файле целей не хранятся — там `"x-goog-api-key": "$env:GEMINI_API_KEY"`,
  значение подставляется в момент запроса. Форма `$env:ИМЯ:префикс` даёт
  «префикс + значение» — так собирается `Authorization: Bearer` для
  OpenRouter. Неизвестная переменная не уезжает в заголовок литералом:
  ссылка вычищается, пустые заголовки не отправляются.

### Fixed
- **Тело ответа дочитывалось и выбрасывалось.** `reachability` измеряла TTFB и
  закрывала соединение, поэтому разобрать ответ было нечем. Теперь тело
  читается с ограничением по размеру и времени, а прежнее поведение целей без
  правил сохранено: там вердикт по-прежнему ставится по одному факту ответа.
- **Слишком длинный ответ не подвешивает проверку.** Дочитывание ограничено и
  по байтам, и по секундам: сервис, отдающий гигабайт, больше не держит
  воркер.

### Verified
- 30/30 проверок в `singbox-subscribe/source/tests/test_api_rules.py`;
  правила читаются ИЗ КОНФИГА, а не из копий в тесте.
- Боевой прогон на 60 живых серверах с настоящими ключами: получены и `ban`
  (`gemini`, `400`, регион не поддерживается), и `ok` (метаданные модели,
  счёт моделей) — то есть проверка различает запрет и разрешение, а не всегда
  отвечает одинаково.
- Повторный прогон по той же базе не делает ни одного запроса: вердикты
  свежие, строки лежат с `checked_by=api`.
- `check_repo.py` — `RESULT: READY`.

## [2.8.0]

### Fixed
- **Отбор «лучших» выбирал не тех — теперь ранжирование по задержке до
  КОНКРЕТНОЙ цели, а не по скорости.** Раньше «лучшим по gemini» мог стать
  сервер, который gemini вообще не проходил: рейтинг считался по гибриду
  скорость/пинг, а скорость у сервера одна на все сервисы и к конкретному
  сайту отношения не имеет. Теперь чекер reachability сохраняет измеренный
  TTFB до каждой цели (новая колонка `servers.service_pings`,
  `{"youtube": 200, "google": 100}`), и лучшие в группе [youtube]
  определяются по задержке именно до YouTube.
- **Замер задержки выбрасывался.** TTFB измерялся и тут же терялся: в базу
  уходил только факт «цель достигнута» — тег. По тегу нельзя отличить сервер
  с откликом 200 мс от сервера с 3000 мс, поэтому «лучший» выбирался
  фактически случайно (по порядку строк в базе).
- **Сервер без замеров больше не становится лучшим.** Считать его лучшим не
  на чем; он остаётся в группе и уходит в резерв. Раньше в этой ситуации
  победитель определялся порядком строк, а метка выглядела осмысленной.
- **Замеры схлопывались в один ключ `Global` — метки `[cloudflare-best]`
  не появлялись никогда.** Цель группы merge писалась в `service_pings`
  только под именем группы. Сервер, прошедший ОДНУ cloudflare, получает
  профиль `cloudflare` (группа сворачивает теги лишь при 3 из 3), а замер
  ложился как `{"Global": 250}` — отбор не находил замера для группы

### Added
- **Внутренний браузер проекта (`browser/`) — проверка сервисов из-под сессии.**
  Отдельный подпакет запускает Chromium через Playwright с сохранённым профилем

  - `browser/login.py` — ручной вход один раз, профиль сохраняется;
  - `browser/check.py` — проверка одного сервиса через прокси сервера;
  - `browser/batch.py` — пакетная проверка, по одному Playwright на поток

  - `browser/portable.py` — экспорт и импорт сессии шифрованным файлом

    аргументом командной строки: он попал бы в историю оболочки и в список

  пакету, поэтому `cd` не нужен. Шесть отдельных обёрток были бы тем же самым
  шестью файлами ради одной строки — от них отказались.
- **Чекер `browser_service` в конвейере.** Идёт после `reachability`, берёт

- **Вердикт `unstable`.** Сервер отвечает по-разному от захода к заходу. Ни
  рабочий, ни забаненный: метку по нему не ставим и не снимаем, следующий
  прогон спросит снова. Появился потому, что замеренный сервер за один час дал
  `ok`, `ok`, `ok`, затем заглушку и полную смерть — один удачный заход принял

- **Проверка стабильности: `ok` требует ДВУХ подтверждений подряд.** Заглушка
  подтверждения не требует (отсекается на первом заходе).
- **`browser_trust.py` — приведение базы в соответствие.** Снимает метку сервиса
  у серверов, чей вердикт не подтверждён браузером. На боевой базе из 56
  серверов с `[gemini]` подтверждены были РОВНО 2.
- **Диагностика запуска sing-box.** `SINGBOX_CAPTURE_LOG=1` пишет вывод процесса
  рядом с конфигом, а причина отказа попадает в лог. Раньше `stderr` уходил в

### Fixed
- **`PIPELINE_CHECKERS` не действовал вообще.** При `selection=None` функция
  `build()` брала ВСЕ найденные чекеры, игнорируя настройку: отключить чекер
  через `.env` было нельзя в принципе, и в логе всегда стояли все шесть.
- **Гонка при выделении портов — причина деления батчей «не стартовал».**
  Проверка «порт свободен» и запись в `_RESERVED_PORTS` были разнесены, и два
  потока успевали взять один номер: оба видели его свободным, оба удачно
  биндились (проверка закрывает сокет и порт не удерживает) и оба записывали.
  Замерено на 16 параллельных батчах: 4–6 падали с «bind: Only one usage of
  each socket address», выданные наборы пересекались (`[51487..51490]` и
  `[51488..51491]`). Подбор целиком переведён под один замок, порт
  регистрируется сразу при выдаче.
- **Порты брались из эфемерного диапазона Windows.** Обход начинался от порта,
  который только что выдала ОС (49152–65535), то есть система соревновалась с
  нами за те же номера — отсюда `WSAEACCES` на `bind` при формально свободном
  порте. Теперь диапазон ниже эфемерного: 40000–49000.
- **`stop_singbox` не снимал дерево процессов на Windows.** `terminate()`
  вызывался первым, и при успехе функция выходила по `return`, не доходя до
  `taskkill /T`. Найдено 10 осиротевших `sing-box.exe`, старейший работал
  3.5 суток и держал listen-порт. Порядок обращён: сначала дерево, потом
  `terminate()`.
- **`ports_ready` сканировал порты последовательно.** На Windows connect к
  закрытому порту на localhost висит весь свой таймаут (замерено: ровно 0.35 с),
  поэтому обход 100 портов стоил 35 с — дедлайн 10 с истекал, едва начавшись, и
  батч объявлялся «не стартовавшим», хотя sing-box поднимался. Опрос параллельный.
- **`Global` затирал все остальные метки при экспорте.** Строка
  `if any(t == global_tag ...): return f"[{global_tag}]"` возвращала РОВНО один
  тэг. На боевом whitelist 11 строк из 13 вышли как `[Global]` в одиночку, хотя
  в базе у них были `openrouter`, `openai`, `youtube`, `speed-slow`. Теперь
  `Global` сворачивает только тэги своей группы (цели `generate_204` из блока
  `merge`), остальные сохраняются.
- **`run_exclusive` отпускал замок, пока sing-box ещё работал.** По таймауту
  `wait_for` прерывал ожидание, но поток продолжал жить и держать порты, а замок
  был уже свободен: следующий чекер стартовал поверх работающего предыдущего.
  Замок снимается колбэком завершения, а не ожидающим.
- **`run_probe_batch` падал с `TypeError` вместо деления батча.** `results`
  передавался и позиционно, и через `**half` — ветка деления не делила батч, а
  роняла прогон чекера целиком.
- **Методы банов отсутствовали в `ServerStore`.** `service_check` вызывал
  `banned_proxy_keys()` и `record_service_bans()`, которых в классе не было —
  запись вердиктов падала с `AttributeError`.
- **`browser_service` падал на обращении к внутренностям файлового кэша**
  (`cache._lock`, `cache._data`) после переезда в базу: у DB-версии этих
  атрибутов нет. Добавлен публичный метод `known_keys()`.
- **`PIPELINE_BROWSER_MAX_CHECKS` по умолчанию 0** (без ограничения) — прежний
  дефолт 25 конфликтовал с новой логикой.

## [2.6.0]

### Changed
- **Метка профиля собирается по группе целей, а не по «прошёл все цели».**
  В `config/reachability_targets.json` появился блок `merge`: список групп, у
  каждой — теги целей и порог `min_matches`. Сервер, набравший порог,
  помечается в колонке `capabilities` ОДНИМ общим тегом вместо тегов группы,
  и ровно этот тег выводится из базы на экспорте.
  - `Global` теперь это «любые 3 из 3» целей `gstatic`, `yandex-portal`,
    `cloudflare` — три `generate_204`. Прежнее правило «прошёл ВСЕ цели
    профиля» отменено: порог задавал не список целей, а его длина, поэтому
    девятая цель отнимала метку у всех разом. На боевой базе полный набор из
    восьми целей имел 1 сервер из 38.
  - Групп может быть несколько и с разными порогами; `remove_tags: false`
    оставляет теги целей рядом с общим, `min_matches` меньше длины списка
    задаёт «любые N из». Порог вне диапазона `1..len(tags)` зажимается:
    «3 из 2» не набрал бы никто, «0 из 3» — любой сервер.
  - Группа, ссылающаяся на цель, которой нет в профиле, пишет WARNING:
    опечатка не ломает прогон, но делает группу недостижимой. Этой проверкой
    поймана опечатка `yandex-cloudflare` в первой же версии блока.
- **Обычные цели больше не требуют совпадения всех.** Сервер получает теги
  тех целей, которые прошёл (`[gemini]`, `[openai]`, ...). Раньше ветка
  «прошёл все -> Global, иначе список тегов» делала профиль либо пустым,
  либо полным.
- **Общие теги групп вытесняются при новом прогоне.** `compute_target_tags`
  берёт имена групп из `merge`, а не только имена целей: сервер, набравший
  сейчас две `generate_204` из трёх, больше не носит `[Global]`.

### Added
- **Три цели группы Global** в `reachability_targets.json`:
  `gstatic` (https://www.gstatic.com/generate_204), `cloudflare`
  (http://cp.cloudflare.com/generate_204 — проверено запросом: по http
  отвечает 204, по https отдаёт 403) и `yandex-portal` — тот же URL
  `https://yandex.ru/portal/generate_204`, что у цели `yandex`, но под
  отдельным именем: имя цели — ключ пробы и тега, и вторая запись с именем
  `yandex` молча вытеснила бы первую.
- **Блок `merge` — единственный источник групп.** Запись это `tag` и `list`
  целей, например:
  ```json
  "merge": [
    {"tag": "Global", "list": ["gstatic", "yandex-portal", "cloudflare"],
     "min_matches": 3},
    {"tag": "Core",   "list": ["openai", "gemini"]}
  ]
  ```
  Настройки `REACHABILITY_MERGE_TAGS` больше нет: правило приходит из файла
  рядом с профилем целей, а не из окружения, и не может с ним разойтись.
- **Группа `Yandex` в шаблоне `sbc-1.14.json`** — пара `Yandex-ping`/`Yandex`
  по образцу остальных целей.

### Fixed
- **Профиль терял совпадения, если две цели делят один тег.** Теги в профиле
  собирались списком с повторами, и цель, чей тег уже был добавлен, съедала
